# 数据库说明

脚本针对 MySQL 8.0.16 或以上版本，新部署使用独立的 `panyue_agent` 库。所有 `DATETIME` 按 UTC 约定存储；Compose 内 MySQL 默认时区设为 UTC，展示时由应用转换为北京时间。外部客户端写入也必须遵守该约定。

| 表 | 内容 |
| --- | --- |
| `t_company` | 企业快照、核验状态及未来企业库 ID |
| `t_source_record` | 经授权保存的原始信息或证据摘要 |
| `t_company_signal` | 招聘扩张或明确求租信号 |
| `t_building` | 楼宇配置 |
| `t_lead` | 匹配评分及人工审核状态 |
| `t_lead_evidence` | 线索关联的来源记录与可选信号 |
| `t_lead_followup` | 人工跟进记录 |
| `t_agent_run` | 工作流运行记录 |
| `t_monitor_schedule` | 按企业和来源记录计划及最近检查时间 |
| `t_api_call_log` | 每次外部接口调用的状态及已知费用 |

## 身份、去重和证据

- `credit_code` 可为空，非空值唯一；已核验状态要求有 18 位代码。校验位真实性及工商核验仍需业务服务实现。无已核验代码时企业应保持 `PENDING`；不能仅凭名称自动合并企业。
- 有稳定来源 ID 时，`(source, record_type, external_id)` 唯一；无 ID 时，以同来源、同类型和规范化内容的 SHA-256 小写十六进制哈希去重。采集器负责确定稳定的规范化方法及处理同一 ID 内容更新。两条不同来源 ID 的记录即使内容相同也不会被哈希索引误合并。
- 来源记录可以暂时不关联企业，但只有关联到企业后才能成为其信号或线索证据。联合外键阻止将其他企业的来源或信号挂到线索上；类型约束要求招聘扩张引用招聘来源、明确求租引用求租来源。
- `raw_payload` 允许为空；按数据授权只保存获准保留的原文、字段或必要摘要。`t_api_call_log` 不存 API 密钥、完整请求或响应；运行记录也应脱敏。

## 审核与评分

一家公司对同一楼宇保留一条当前线索；重新分析应更新该线索，审核与历史策略需要后续服务明确。线索默认 `PENDING_REVIEW`；数据库要求 `APPROVED` / `REJECTED` 有审核人和时间，只有 `APPROVED` 才能填写外部 `crm_lead_id`。数据库约束不能证明审核人身份，也不能独立授权状态变更；后续业务服务必须实现身份认证、角色校验、状态流转、审计、幂等发布和跟进权限，并以事务保证每条推荐线索附有至少一条可追溯证据。

线索意向、匹配、可信及优先级为 0～100 整数；信号的 `confidence` 是 0～1。数据库只约束范围，不计算分数。后续规则应按需求实现 `priority = 0.45 × match + 0.40 × intent + 0.15 × confidence` 并明确取整方式。招聘扩张不能直接认定为明确求租；未知租金不能被当成不匹配。

`t_building.min_area` 与 `max_area` 当前只保存本项目的目标面积，而非已核实空置房源。楼宇租金、地址及配套留空；需要核实后再使用。

## 与现有系统的边界

`enterprise_id`、`reviewed_by_user_id`、`created_by_user_id` 和 `crm_lead_id` 是预留的外部系统标识，没有跨库外键；真实身份映射和授权由未来接口负责。当前没有数据同步实现，没有直接访问既有数据库，也不会自动创建正式 CRM 线索。

一个来源 ID 对应一条当前记录；如需保留每次变更的历史版本，后续应新增版本/变更模型，不能依赖覆盖后的 `raw_payload` 恢复历史。
